# DefectDock 首次标注与首个模型实施计划

更新日期：2026-09-04。

状态：计划已编写，功能尚未实施。本轮不安装依赖、不下载权重、不启动服务、不修改业务代码。

本计划根据用户最新要求，将近期重心由商业交付与管理能力扩展，调整为个人本地使用的首次标注与训练闭环。历史计划保留作为背景；近期开发顺序以本文件为准。

## 1. 本期目标与边界

必须完成三项：

1. 没有已训练或已激活项目模型，也能进入“基础模型辅助标注”。
2. 能在网页上预览、修改、确认标注，再训练第一个缺陷模型。
3. 保留“当前项目模型批量标注”，展示模型名称、版本、类别、实际可用状态及不可用原因。

主流程：上传图片 → 基础模型候选/人工标注 → 逐图审核 → 已审核标注版本 → 训练快照 → 首次训练 → 注册并由用户激活 → 项目模型批量标注。

基础模型是辅助工具，不承诺零样本准确识别板材缺陷；“没有检出”不等于“没有缺陷”。流程可执行与模型有效性分别验收。

本期仅支持矩形目标检测标注。沿用浅色、清新界面；保留 TorchVision 历史能力、数据版本、快照及 CVAT/YOLO 导入。暂不做视频监控平台、云端 LLM、多人协作、自由多边形编辑、多机调度和新的部署格式。

## 2. 代码核查基线

| 现有实现 | 本期缺口 |
| --- | --- |
| `api/app.py` 的 `POST /api/datasets/{id}/auto-annotations` 使用指定模型或全局激活模型，并要求模型已批准 | 没有独立基础模型入口；默认无模型时抛出英文错误 |
| `data/auto_annotations.py` 原子生成候选版本，记录模型和图片哈希 | 不支持基础模型、提示词、候选框编辑及逐图审核；置信度没有随 YOLO 文本保存 |
| `apps/web/src/components.tsx` 提供图片上叠框预览和整版批准按钮 | 没有画框、拖拽缩放、删除、类别修改、保存草稿和逐图确认 |
| 训练 schema、表单和推理服务绑定 TorchVision / Faster R-CNN | 引入 YOLO 必须同时适配训练、制品注册、激活和推理，不能只增加一个选项 |
| 已有冻结快照、版本哈希、训练任务、模型注册和回滚 | 应复用，不重建第二套生命周期 |
| 文档和 CI 禁止 Ultralytics / AGPL 依赖 | 与用户当前个人使用方向不同，需先形成明确的许可策略变更 |

核查入口：`src/defectdock/config/schema.py`、`engines/base.py`、`inference/detection.py`、`domain/datasets.py`，以及前端 `DatasetDetailPage.tsx`、`TrainingPage.tsx`、`ModelsPage.tsx`。

工作区已有未提交的网络限流等改动；实施时保留这些改动，不覆盖、不回滚，也不把它们算作本计划产出。

## 3. 模型选型与个人使用策略

### 3.1 首期技术选择

| 用途 | 首选方案 | 使用边界 |
| --- | --- | --- |
| 文本提示生成候选框 | Ultralytics YOLO-World，先验证 `yolov8s-worldv2.pt` | 支持自定义文本类别；在用户板材图片上的检出能力必须实测，不用普通 COCO 模型冒充缺陷基础模型 |
| 点/框交互辅助 | MobileSAM，先验证 `mobile_sam.pt` | 用户选择缺陷类别并点选/框选区域；模型只辅助分割，不决定缺陷语义；首期转为外接矩形 |
| 第一个专用检测模型 | Ultralytics YOLO11n，先验证 `yolo11n.pt` 的迁移学习 | 只用审核后的用户数据训练；保留已有 TorchVision 选项及旧模型读取能力 |

以上是工程首选，不是已验证的本机配置。阶段 P0 记录并锁定实际通过的 Python、Torch、Ultralytics、额外文本编码依赖及权重版本/来源/SHA256，不使用浮动 latest 作为验收环境。

YOLO-World 的提示词与业务类别分离：中文类别名照常展示；提供可编辑英文提示词字段，每个提示词显式映射到稳定的 dataset class_id。首期不依赖在线翻译；映射不完整时禁止批量执行。模型输出的类别索引不能直接当成数据集类别索引。

不预设某模型一定能在当前 GPU 运行：执行前检测驱动、可用显存、Torch/CUDA 和 CPU 路径。先小样本、batch=1；单机串行占用 GPU，标注与训练互斥，切换模型释放缓存。显存不足给出降低尺寸、切换 CPU 或手工标注的明确选择，不无限重试。

## 4. 产品交互

### 4.1 数据集详情：区分两个入口

“基础模型辅助标注”：无需项目模型。显示可用方式、模型准备状态，支持先选 1–3 张图片试标，再对选定范围批量执行。人工标注入口始终可用，不被依赖安装/模型下载阻断。

“当前项目模型批量标注”：显示实际将使用的模型名称/版本、引擎、类别顺序、来源运行、权重完整性和运行时状态。明确“当前”是现有全局激活模型，不暗示已经实现数据集绑定。

- 没有激活模型：按钮禁用，提示“暂无项目模型，可先使用基础模型辅助标注”，并给出跳转。
- 未批准、类别不匹配、权重丢失/校验失败、运行时缺失：显示具体原因及对应操作。
- 已就绪：允许调整阈值、选择图片范围，提交时固定 model_version_id 和 artifact hash；执行中切换全局模型不改变本任务。
- 普通健康检查不等于模型已成功加载；状态区分配置存在、权重就绪、运行时就绪及最近加载结果。

### 4.2 标注编辑页

新增 `/datasets/:datasetId/annotations` 路由，通过 URL 标识草稿/版本/当前图片，支持刷新恢复。

- 左侧图片与审核状态，中间可缩放平移的图像画布，右侧类别、候选框及来源列表。
- 添加框、选择框、拖动、调整尺寸、删除、修改类别；支持撤销/重做、上一张/下一张、快捷键，并避免输入框内误触删除快捷键。
- AI 候选显示置信度与来源；人工新增框不编造置信度，修改后保留原始候选来源。
- MobileSAM 支持点/框提示，掩码预览及外接矩形确认；用户始终可以放弃结果手工画框。
- 草稿自动保存有防抖和明确的“保存中/已保存/保存失败/有冲突”状态；失败不能显示成功。切图与离开页面提示未保存修改。
- 逐图状态：未审核、已确认有标注、已确认无目标。修改已确认图片后撤销其确认状态。
- 未检出、推理失败、未处理、人工确认无目标必须分别表达；不能把空文件一律视为已审核负样本。
- 首期批准必须覆盖当前数据集全部图片；仍有未审核或失败图片时显示数量并阻止批准，不做容易混淆的部分冻结。
- 完成审核后点击“确认标注并准备训练”，展示类别计数、负样本和划分结果，再生成快照并进入训练页；训练仍由用户点击提交。

### 4.3 反馈与资源准备

保持现有浅色设计，优先内联状态和进度，toast 只提示关键完成/错误，不只依赖短暂弹窗。

- 模型准备展示依赖/权重状态、下载来源、实际大小与进度、失败原因、重试和离线导入入口。
- 不让网页 API 执行任意 pip/shell。依赖由受控本地安装脚本/CLI 准备；网页读取能力并提供明确操作说明。
- 权重下载仅允许模型目录中受控条目；请求不能指定任意 URL 或本地路径。下载校验后原子落盘；不下载到 Git 仓库。
- 首次下载说明会连接上游，但图片及标注保持本地；首期没有云端识别或数据上传。
- 自动标注展示已处理/总数、候选数量、失败图片，支持取消；刷新页面可恢复任务状态，不自动重放写请求。

## 5. 数据与后端契约

### 5.1 分离基础模型与项目模型

增加统一预测适配层，但分别管理：基础模型目录记录 provider/model_id、提示能力、权重来源与许可、缓存状态；项目模型仍进入现有注册表。

基础模型无需注册、审批或激活为项目模型；使用基础模型也不得覆盖全局 active_model。YOLO 与 TorchVision 按显式 engine/模型元数据选择加载器，禁止根据 `.pt` 扩展名猜格式。

模型目录依赖懒加载，核心轻量安装仍可启动；未安装 AI 依赖时提供可操作提示，不能因导入 Ultralytics 让 API 启动失败。

### 5.2 可编辑草稿与不可变版本

- 新增标注草稿、逐图标注/审核记录和任务状态表，使用 Alembic 迁移并覆盖旧库升级。
- 草稿采用 revision 乐观锁；过期保存返回 409 并提示重新加载，不能覆盖另一页面的新修改。
- 框保存稳定 ID、class_id、像素 xyxy、原图尺寸、来源和可选置信度；视图缩放坐标由前端转换，后端校验有限数、边界和正面积。
- 记录 parent_version、模型/权重哈希、提示词和类别映射、参数、图片集合/哈希、人工修改与审核信息。
- 草稿可变；发布生成新的候选不可变版本，审批只针对固定内容及哈希；既有 approved 版本、图片和训练快照不原地修改。
- 编辑现有候选版本时先派生草稿，不能重写候选版本目录。只在用户明确选择时切换当前标注头。
- 已冻结数据集保持只读。本期需要追加图片/继续训练时提供派生新数据集修订的操作，保留父数据集关联；旧快照绝不解冻或覆盖。
- 空标注必须带人工确认无目标状态；YOLO 五字段文本继续作为训练兼容格式，置信度、来源、审核状态保存在独立 manifest/元数据中。

### 5.3 自动标注任务

新批量流程采用持久化任务 ID + 轮询，状态为 queued/running/succeeded/failed/cancelled；逐图记录结果与失败，不把长推理塞进一次等待完成的 HTTP 请求。

- 锁定图片集合、数据修订、类别映射、源草稿 revision、模型版本和参数；完整分页读取图片，不能静默只处理现有接口上限的前 5000 张。
- 任务结果进入独立候选草稿，默认不覆盖已有人工标注。合并须由用户选择并校验草稿 revision。
- 重复提交使用幂等键；取消保留已完成候选但不批准，失败图片可定向重试。
- 服务重启将未完成任务标为 interrupted/可重试（可作为失败原因），首期不承诺 GPU 中途无损续跑；不得留下永久 running。
- 复用单机资源排他和任务审计，不另建分布式队列。取消在逐图/训练回调安全点生效，并如实展示“正在取消”。

### 5.4 拟新增接口（实现前以类型与测试固定）

| 接口 | 职责 |
| --- | --- |
| `GET /api/annotation-capabilities?dataset_id=...` | 基础模型、项目模型及逐项不可用原因 |
| `POST /api/base-models/{id}/prepare` | 仅下载/校验允许的权重，返回准备任务 ID，不安装任意依赖 |
| `POST /api/datasets/{id}/annotation-jobs` | 基础模型或明确项目模型创建批量任务 |
| `GET /api/annotation-jobs/{id}`、`POST .../{id}/cancel` | 查询进度与取消 |
| `POST /api/datasets/{id}/annotation-drafts` | 新建空草稿或从版本派生 |
| `GET /api/annotation-drafts/{id}` | 查询草稿、revision 与审核计数 |
| `PUT /api/annotation-drafts/{id}/images/{image_id}` | 保存框及逐图审核状态，要求 revision |
| `POST /api/annotation-drafts/{id}/assist` | 当前图片点/框辅助建议，不自动覆盖草稿 |
| `POST /api/annotation-drafts/{id}/publish` | 发布固定候选版本，再复用审批/快照链路 |

旧 `auto-annotations` 接口保持兼容并补中文可理解的结构化错误；新 UI 使用任务接口。新增接口沿用现有认证、请求限制、限流和审计，校验资源归属。不能因为是本地模式就信任任意路径或任意序列化权重。

- [ ] 异常端到端：无网络、缺依赖、权重损坏、类别不匹配、显存不足、取消/重启、草稿保存冲突和失败。
- [ ] 缩放/平移/不同分辨率/EXIF 方向下框坐标正确，键盘与鼠标均可操作，保存失败不丢失页面内修改。
- [ ] 旧 TorchVision 模型、已有批准标注、YOLO/CVAT 导入和历史快照仍可读取使用；未审核草稿不能绕过后端进入训练。
- [ ] 更新使用文档和验收记录，分别记录硬件、真实运行结果、模型效果及已知限制。

## 7. 最终验收场景

用现有板材数据集的副本演示，保留原始数据和历史状态：

1. 模型注册表为空时，“基础模型辅助标注”仍可进入；依赖未就绪时能看到准备指引。
2. 执行真实基础模型得到候选或明确的无检出结果；能通过点/框辅助或手工补足，而不是报“没有激活模型”。
3. 在网页新增、移动、缩放、删除框和修改类别，保存并刷新后内容一致。
4. 空图需显式确认无目标；全部图片确认前不能批准。发布后可追溯基础模型与人工修改来源。
5. 审核完成后生成独立快照并实际训练；样本过少时显示仅用于流程验证，不能把训练集表现当泛化效果。
6. 新模型完成注册、用户激活和真实推理；批量标注入口准确显示实际使用版本与类别。
7. 整个过程不要求用户手写 YOLO 文本，也不改写旧快照；预先准备好模型后不依赖云端识别服务。

流程验收不设虚构的精度/秒数承诺。实测报告记录候选保留/修改/删除情况、人工用时和错误案例；缺少独立真实验证数据时明确“效果未验收”。

## 8. 本期不做与实施纪律

- 不为了接入标注功能整体迁移 EasyAIoT；只参考其候选→审核→专用模型回用的产品流程。
- 不建设多租户、复杂审批、集群、视频告警、模型商城或云端付费能力。
- 不同时接入大量模型；首选方案不适配时先报告真实证据，再决定替代路线。
- 不对原始数据执行无确认覆盖，不为了演示自动批准 AI 标注，不用模拟结果冒充真实推理。
- 本轮仅提交计划文档；后续收到开始实施的指令后按 P0 → P1 → P2 → P3 → P4 → P5 推进。
