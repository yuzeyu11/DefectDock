# DefectDock 第一性原理分析与实施校准

> 评估对象：`defectdock` v0.1.0（首次 Git 提交建立前的审计快照）
>
> 评估日期：2026-08-29
>
> 评估方法：从工业视觉交付的不可约约束出发，对照仓库当前代码、测试、运行方式和商业合规边界逐项核验
>
> 状态说明：问题清单记录开始执行前的审计起点，不自动代表当前完成状态；实施进度必须以 Git、测试、制品和验收记录为准。

---

## 1. 问题的本质

DefectDock 要解决的不是“再做一个训练 Demo”，而是：**把工业视觉算法变成可验证、可部署、可运营、可维护、可商业交付的产品能力。**

原报告提出的五条约束方向正确，但还不完整。面向真实客户交付，至少需要以下八条不可约约束：

| # | 第一性约束 | 工程含义 |
|---|---|---|
| 1 | 数据质量决定能力上限 | 数据、标注、划分和泄漏必须经过质量门禁 |
| 2 | 结果可复现 | 必须记录代码、依赖、配置、数据、权重、环境和随机性，而不只是配置哈希 |
| 3 | 全链路可追溯 | 上线模型必须可回溯到训练运行、数据快照、标注版本、审批和操作者 |
| 4 | 工业验收口径有效 | 以漏检、误报、节拍和分层表现为核心，不能只看学术指标 |
| 5 | 部署就绪 | 模型必须在目标硬件和真实输入链路上完成端到端验证 |
| 6 | 安全与责任边界清晰 | 本地单机模式和网络服务模式必须有不同的暴露、认证和审计要求 |
| 7 | 可运营、可恢复 | 任务、数据库、模型激活和服务重启都必须有明确恢复与回滚语义 |
| 8 | 商业合规与成本可控 | 源码、依赖、模型权重、数据集和镜像均需合规；资源消耗必须可测量 |

因此，产品护城河不是某个公共模型，而是把以上约束固化为无法轻易绕过的工程契约。

## 2. 当前设计中值得保留的部分

| 能力 | 当前设计 | 评价与边界 |
|---|---|---|
| 配置约束 | `config/schema.py` 使用严格 schema，拒绝未知字段 | 正确；仍需补依赖、环境和权重指纹 |
| 运行追踪 | `db/store.py` 记录运行、配置、数据集版本和指标 | 骨架正确；仍缺数据库迁移和更强外键关系 |
| 状态约束 | `domain/runs.py` 限制非法状态跃迁 | 应保留，并由任务恢复和取消测试覆盖 |
| 数据门禁 | 数据检查、冻结和内容哈希 | 方向正确；当前“冻结”还不等于物理不可变快照 |
| 工业评测 | 阈值扫描、召回与错误分析 | 方向正确；“误检率”命名和统计口径需要修正 |
| 引擎隔离 | `engines/base.py` 的 `TrainingEngine` Protocol | 抽象合理；一个实现尚不足以证明可替换性 |
| 依赖隔离 | Torch 训练栈懒加载 | 有利于 API 启动、测试和轻量安装 |
| Ultralytics 边界 | CI 脚本扫描导入和依赖声明 | 是必要防线，但不是完整的软件供应链合规体系 |

应保留的产品判断是：**先把可复现、可追溯、可验收、可回滚做成产品契约，再扩展模型数量。**

## 3. 必须修正的关键认识

### 3.1 “相同配置和数据得到相同结果”表述过强

当前的 `config_hash` 和配置快照只能证明“输入配置可追踪”，不能单独证明结果可复现。训练结果还受以下因素影响：

- 代码提交 ID 与工作区是否干净；
- Python 与操作系统版本；
- 完整依赖锁及其制品哈希；
- CUDA、cuDNN、驱动和 GPU 型号；
- 预训练权重来源、许可证与 SHA256；
- 数据快照和标注快照的清单哈希；
- 随机种子、确定性算子设置和数据加载并发；
- 允许的数值误差和指标容差。

正确目标不是承诺逐位一致，而是：**在声明的环境、随机性策略和容差范围内可重复，并能解释差异。**

### 3.2 当前“误检率”公式不能直接称为经典 FPR

如果实现使用 `FP / (TP + FP)`，它表达的是假发现比例（FDR），等价于 `1 - precision`，不是经典定义的 `FP / (FP + TN)`。

工业现场通常更应同时报告：

- 缺陷级召回率与漏检率；
- 每张图、每个工件或每小时的误报警数量；
- FDR / Precision；
- 按缺陷类别、尺寸、产线、设备和批次分层的表现；
- 置信区间或样本量；
- P50/P95/P99 延迟、吞吐量、显存和 CPU/GPU 占用。

仓库中相关字段和报告应采用不会混淆的名称；若保留“误检率”作为业务术语，必须在报告中明确公式和统计单位。

### 3.3 数据集 `freeze` 目前主要是逻辑状态，不等于不可变

数据库里的冻结标记不能阻止底层图片或标注文件被直接修改。一个可审计训练运行应引用独立的数据快照，至少包含：

- 图片、标注、类别映射和 train/val/test 划分清单；
- 每个文件的内容哈希与快照整体哈希；
- 标注版本 ID，而不是通过目录名猜测“最新版本”；
- 训练运行到数据快照的数据库外键；
- 快照创建后禁止原地修改，变更必须产生新版本。

### 3.4 “排除 Ultralytics”不等于已经完成商业合规

许可证边界还应覆盖：

- Python、前端和系统依赖的 SPDX 许可证与 NOTICE；
- 复制或改写的第三方源码及其出处；
- 动态导入、可选依赖和插件；
- 预训练模型、数据集、示例图片和字体；
- Docker 基础镜像与系统包；
- 发布制品的 SBOM、漏洞扫描、许可证清单和归档证据。

Ultralytics 检查应保留，但定位为“专项禁止规则”，上层还需要通用供应链合规门禁。

## 4. 问题清单

严重度定义：**P0 = 阻塞可安装、可运行或可审计基线；P1 = 阻塞完整产品主链路；P2 = 规模化和扩展能力。**

### P0-0：尚未建立可回退的 Git 工程基线

- 当前仓库没有首个提交，文件均处于未跟踪状态。
- 因此无法可靠审查变更、定位回归、建立版本号，也不能证明某次训练对应哪份代码。
- 先完成仓库清点、敏感信息与大文件检查、基础测试，再创建首个可运行基线提交和标签；在此之前不要把当前状态称为“工程基线”。

### P0-1：工作区路径错误地锚定在 Python 包安装位置

- **位置**：`src/defectdock/cli.py`、`src/defectdock/api/app.py` 中由 `__file__` 推导的 `PROJECT_ROOT`。
- wheel 安装后，数据库、激活配置、输出和示例配置可能指向 `site-packages`；该位置可能只读，也不属于客户项目数据。
- 需要明确区分：
  - 包内只读资源：通过 `importlib.resources` 读取；
  - 用户工作区：由 CLI `--workspace`、`DEFECTDOCK_WORKSPACE` 或受控默认值决定；
  - 应用状态目录：数据库、日志、缓存和激活状态；
  - Docker 数据卷：显式映射到例如 `/data`。
- 同一套设置对象必须注入 CLI、API、任务管理器和测试，禁止各模块自行推导根目录。

### P0-2：当前 P0 改造处于“部分写入、尚未验证”状态

仓库已出现训练任务管理、取消、训练快照、直接标注上传和新增 API 端点等改动，但尚未完成相应测试和整体验证。已知风险包括：

- 全局 `app = create_app()` 在导入期创建数据库、目录和任务管理器；多 worker 下可能重复恢复任务或竞争资源；
- 进程内线程池没有跨进程单 GPU 排他机制；
- 新增 API、取消语义、快照和恢复路径尚未经过端到端测试；
- 模块级路径常量与注入的工作区可能并存，造成状态分裂；
- 原始数据冻结与“仅允许已标注数据进入训练”的约束尚未完全闭合。

处理原则：**先稳定、补测、验证，再继续增加功能。未通过验证的代码不计入完成项。**

### P0-3：缺少可验证的干净安装与制品启动证据

- 从源码设置 `PYTHONPATH` 启动成功，只能证明开发树可运行。
- 仍需验证 wheel 安装、非仓库目录启动、只读包目录、数据库初始化、静态资源、Docker 数据卷和健康检查。
- 应把“从干净环境安装并启动”加入 CI 或发布流水线，而不是依赖开发机现状。

### P1-1：安全模式没有明确边界

“先加一个 API Token”只解决了极小部分问题。建议定义两种产品模式：

1. **本地模式**：默认仅监听 loopback，可允许无登录，但明确单用户、可信机器边界。
2. **网络模式**：强制认证、TLS 或可信反向代理、角色授权、审计日志、请求大小限制、上传校验、速率限制和密钥外部注入。

训练提交、取消、模型激活和文件上传属于高风险操作，不能只依赖“端口不公开”的假设。

### P1-2：React + TypeScript 工作台仍是只读骨架

- **位置**：`apps/web/src/App.tsx` 及相关前端模块。
- 当前主要展示健康状态、运行列表和示例配置，尚未闭合真实操作链路。
- 首个产品纵切应是：**创建/导入数据集 → 上传标注 → 质量检查 → 冻结快照 → 提交训练 → 查看日志与指标 → 评测 → 注册并激活模型 → 回滚。**
- 前端应复用后端生成或共享的 API 类型，统一错误模型、加载状态、取消操作和权限提示。

### P1-3：模型注册、原子激活和回滚缺失

- 当前激活主要依赖 `.defectdock/active_model.json` 指针和进程内推理对象替换。
- 需要最小模型注册表：模型版本、来源 `run_id`、数据快照、指标、制品哈希、状态、审批人和时间。
- 激活必须验证制品完整性，采用原子切换和并发保护；失败时保持旧模型可用；提供明确回滚操作和审计记录。

### P1-4：训练到部署的产物链路没有闭合

- 当前主要产物是 TorchVision checkpoint，缺少稳定的导出契约和目标运行时验证。
- 应先为现有引擎完成 ONNX 导出、数值一致性检查、目标硬件基准和可部署包，再决定是否引入 TensorRT。
- 导出制品也必须记录 opset、输入规格、预后处理版本、依赖与哈希。

### P1-5：数据库没有正式迁移机制

- 随着运行、数据快照、模型注册和审计字段增加，仅靠启动时建表无法安全升级客户现场数据库。
- 需要引入显式 schema version 和迁移工具，覆盖升级、失败回滚、备份与旧版本兼容测试。

### P2-1：通过目录名字典序选择“最新标注版本”

- **位置**：`src/defectdock/api/app.py` 的最新标注加载逻辑。
- 字典序等于时间序是脆弱的隐式契约，命名规则变化会静默选错。
- 应在数据库保存标注版本及当前生效版本，并由 API 显式选择。

### P2-2：训练任务是进程内线程池

- 单机单 GPU 的 P0 阶段可接受，但服务重启无法续训，多 worker 会产生并发风险。
- 短期应限制为单 worker、单训练任务并提供恢复状态；达到多机或长任务需求后再替换为持久化队列，保持公开 API 稳定。

### P2-3：GC10 标签泄漏进通用接口

- 通用数据集接口不应默认绑定某一示例数据集的十个类别。
- 默认标签应为空或必填，GC10 只存在于示例配置、模板或导入向导中。

### P2-4：只有一个训练引擎和一个重量级检测模型

- 当前只有 Faster R-CNN 适配器，无法证明 Protocol 已经在真实差异中稳定。
- 但“第二引擎”不应排在完成首条端到端交付链路之前。
- 选择第二能力时必须由客户场景驱动：轻量检测用于实时节拍，异常检测用于少缺陷样本/无监督场景。`anomalib` 不能替代实时目标检测，二者解决的问题不同。

### P2-5：日志、监控和资源治理仍不完整

- 需要结构化日志、请求/运行关联 ID、训练事件持久化、日志轮转和敏感信息脱敏。
- 需要服务、队列、GPU、推理延迟、错误率和磁盘空间指标。
- 需要配置上传大小、并发数、磁盘配额、运行超时和产物清理策略，避免客户机器被耗尽。

## 5. 成熟度校准

| 能力维度 | 当前可信状态 | 达到可交付仍缺什么 |
|---|---|---|
| Git 与版本基线 | 缺失 | 首次提交、版本策略、可回退基线 |
| 配置治理 | 已有骨架 | 统一 Settings、环境/依赖/权重指纹 |
| 数据治理 | 已有骨架 | 物理不可变快照、标注版本外键、泄漏检查 |
| 工业评测 | 已有骨架 | 指标正名、业务单位、分层统计、置信区间 |
| 训练执行 | 部分改造、未验证 | 任务补测、单 GPU 排他、恢复和完整 E2E |
| 部署推理 | 源码树可启动 | 干净安装、导出、目标硬件验证、回滚 |
| 前端工作台 | 只读骨架 | 完整主链路、类型契约、异常处理 |
| 安全 | 缺失 | 本地/网络模式、认证授权、审计和上传防护 |
| 模型治理 | 缺失 | 注册、审批、原子激活和回滚 |
| 数据库演进 | 缺失 | schema 版本、迁移、备份恢复测试 |
| 商业合规 | 有 Ultralytics 专项门禁 | 全量 SBOM、权重/数据/镜像审查、NOTICE |
| 可观测与运维 | 初级 | 结构化日志、指标、告警、容量和清理策略 |

“18 个测试文件、CI、懒加载、许可证专项扫描”是良好工程起点，但不能据此认定核心链路已完成。验收应看测试覆盖到的行为、干净环境制品和真实 GPU 端到端证据。

## 6. 修订后的实施优先级

| 顺序 | 阶段 | 具体行动 | 完成证据 |
|---|---|---|---|
| 1 | P0-0 | 清点仓库，验证敏感信息/大文件，建立首个 Git 基线 | 可审查提交、干净工作区、基线标签 |
| 2 | P0-1 | 统一 Workspace/Settings，移除包路径写入 | wheel 从任意目录启动；状态只写入指定工作区 |
| 3 | P0-2 | 收口当前部分 P0 改动，补单元/API/恢复/取消测试 | 后端测试、静态检查和许可证门禁全部通过 |
| 4 | P0-3 | 记录代码、依赖、数据、标注、权重和环境指纹 | 每次运行生成完整 manifest，可校验哈希 |
| 5 | P0-4 | 在 RTX 2060 与代表性小数据集跑通真实 E2E | 上传到训练、评测、产物、推理的可重复验收记录 |
| 6 | P1-1 | React + TypeScript 接通首条产品纵切 | 用户可在 UI 完成主链路，失败状态可理解、可恢复 |
| 7 | P1-2 | 定义本地/网络安全模式 | 默认安全监听；网络模式通过认证、审计和上传测试 |
| 8 | P1-3 | 模型注册、原子激活和回滚 | 可回答“谁在何时激活哪个模型”，失败不影响旧版本 |
| 9 | P1-4 | ONNX 导出与目标硬件基准 | 精度偏差在阈值内，性能报告和制品 manifest 完整 |
| 10 | P1-5 | 数据库迁移和备份恢复 | 旧库升级、失败回滚和恢复测试通过 |
| 11 | P2-1 | 依据真实场景选择第二引擎/任务 | 先有验收场景与性能目标，再复用 Apache-2.0 组件 |
| 12 | P2-2 | 持久化队列、边缘运行时和规模化运维 | 由并发、多机或边缘交付需求触发，不提前堆复杂度 |

这个顺序刻意把“第二引擎”后移：先让一个模型在一条真实业务链路中可安装、可训练、可评测、可部署、可回滚，再扩展模型矩阵。这样才能验证平台契约，而不是继续增加尚未闭合的功能面。

## 7. 阶段性验收门槛

### P0 完成门槛：可重复启动与单机闭环

- 有可回退 Git 基线，工作区干净；
- wheel 在干净环境、非源码目录下安装并启动；
- Docker 数据卷、健康检查和重启行为验证通过；
- 单 worker、单 GPU 的提交、排队、取消、失败恢复语义通过测试；
- 数据/标注快照不可变并带完整哈希；
- RTX 2060 上完成一次代表性端到端训练、评测和推理；
- 后端测试、前端构建、静态检查、许可证和依赖扫描通过。

### P1 完成门槛：可交给试点客户使用

- React + TypeScript 工作台闭合核心操作链路；
- 本地模式与网络模式的安全边界可配置、可测试；
- 模型注册、激活、失败保护和回滚可审计；
- ONNX 制品在目标硬件上完成精度与性能验收；
- 数据库升级和备份恢复有演练证据；
- README、安装、运维、故障恢复、合规和验收手册与代码一致。

### P2 完成门槛：可扩展和规模化

- 第二任务类型或引擎通过契约测试和真实业务验收；
- 持久化队列、资源调度、日志监控和容量策略支撑目标并发；
- 边缘部署、升级、回滚和离线运行形成标准交付包；
- SBOM、漏洞与许可证报告随版本归档。

## 8. 总体判断

DefectDock 的方向和核心抽象值得继续：它应当成为一套围绕工业视觉交付承诺的 **delivery harness**，而不只是模型训练界面。

但当前更准确的描述是：

> 已形成有价值的工程骨架和部分产品契约；源码树后端曾验证可启动，但尚未证明 wheel、容器和客户环境可分发；P0 改造有部分代码未完成测试；仓库也尚无首个可回退提交。因此项目处于“骨架收口与基线建立期”，不能称为稳定可交付版本。

接下来最重要的不是继续加入 LangChain、LangGraph、更多引擎或更多页面，而是用可重复证据闭合第一条主链路。Agent 技术只有在出现明确的多步骤诊断、知识检索或运维编排需求后再引入，并且不能进入训练、审批、激活等关键动作的无审计决策路径。
